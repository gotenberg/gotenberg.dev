The PDF routes work on the PDFs you upload, with litho, Gotenberg's PDF engine. They run [stages](/docs/reference/stages), or read the PDFs and answer JSON.

<RouteTable group="pdf" />

## Run stages

`/forms/pdf/pipe` runs the stages of the `stages` field on the uploaded PDFs, in order:

<Request
  route="/forms/pdf/pipe"
  files={["report.pdf", "annex.pdf"]}
  stages={[{ op: "merge" }, { op: "optimize" }]}
  output="documents.pdf"
/>

The stages take the PDFs in the alphanumeric order of their names. A PDF a stage reads by name, such as the source of `insert`, isn't processed itself.

## Run one stage

Each stage also has its own route, `/forms/pdf/<op>`. It takes the stage's options as form fields, and a list or an object as JSON:

<Request
  route="/forms/pdf/set-metadata"
  files={["report.pdf"]}
  fields={{ title: "Annual report", author: "Finance" }}
  output="report.pdf"
/>

[Stages](/docs/reference/stages) lists every stage and its options.

## Read PDFs

The read routes answer JSON: one entry per uploaded PDF, under its name. They take a `password` field to open encrypted PDFs, and a wrong or missing one answers 400:

<Request
  route="/forms/pdf/info"
  files={["encrypted.pdf"]}
  fields={{ password: "secret" }}
  response={{
    "encrypted.pdf": {
      pages: 3,
      version: "1.7",
      encrypted: true,
      tagged: false,
      linearized: false,
      formFields: false,
    },
  }}
/>

### info

The page count, the PDF version, and whether the PDF is encrypted, tagged for accessibility, linearized for fast web view, or holds form fields:

<Request
  route="/forms/pdf/info"
  files={["report.pdf"]}
  response={{
    "report.pdf": {
      pages: 3,
      version: "1.7",
      encrypted: false,
      tagged: false,
      linearized: false,
      formFields: false,
    },
  }}
/>

### metadata

The metadata, as the `set-metadata` stage takes it: `title`, `author`, `subject`, `keywords`, `creator`, `producer`, `creationDate` and `modDate`, each when set. A PDF without metadata answers `{}`.

<Request
  route="/forms/pdf/metadata"
  files={["report.pdf"]}
  response={{ "report.pdf": { title: "Quarterly report", author: "Finance" } }}
/>

### bookmarks

The bookmarks, as the `set-bookmarks` stage takes them:

<Request
  route="/forms/pdf/bookmarks"
  files={["report.pdf"]}
  response={{
    "report.pdf": [
      {
        title: "Summary",
        pageNumber: 1,
        children: [{ title: "Figures", pageNumber: 2 }],
      },
      { title: "Appendix", pageNumber: 3 },
    ],
  }}
/>

### attachments

The embedded files: name, media type, and their relationship to the document:

<Request
  route="/forms/pdf/attachments"
  files={["invoice.pdf"]}
  response={{
    "invoice.pdf": [
      {
        name: "factur-x.xml",
        mimeType: "text/xml",
        relationship: "Alternative",
      },
    ],
  }}
/>

### form

The form's fields, in a shape `set-form` takes: each field's `name`, `type` (`text`, `checkbox`, `radio`, `button`, `combo`, `list` or `signature`), `value`, and the `pages` it sits on:

<Request
  route="/forms/pdf/form"
  files={["form.pdf"]}
  response={{
    "form.pdf": [{ name: "name", type: "text", value: "", pages: [1] }],
  }}
/>

`options` lists what a choice field takes, and `states` what a checkbox or a radio group takes besides `Off`. A list that selects several has an array `value`. `readOnly`, `required`, `multiSelect`, `editable` and `maxLength` show when they apply. A PDF without a form answers `[]`.

A `pages` field keeps the fields on those pages, as a [page selection](/docs/reference/stages#page-selections):

<Request
  route="/forms/pdf/form"
  files={["multi.pdf"]}
  fields={{ pages: "2" }}
  response={{
    "multi.pdf": [
      {
        name: "total",
        type: "text",
        value: "42",
        pages: [1, 2],
        readOnly: true,
      },
      {
        name: "size",
        type: "radio",
        value: "Off",
        pages: [2],
        states: ["S", "M", "L"],
        required: true,
      },
      { name: "sig", type: "signature", value: "", pages: [2] },
    ],
  }}
/>

### validate

Checks the PDFs against the `profile` field: `PDF/A-1a`, `PDF/A-1b`, `PDF/A-2a`, `PDF/A-2b`, `PDF/A-2u`, `PDF/A-3a`, `PDF/A-3b`, `PDF/A-3u`, `PDF/A-4`, `PDF/A-4e`, `PDF/A-4f`, `PDF/UA-1`, `PDF/UA-2` or `Factur-X`.

<Request
  route="/forms/pdf/validate"
  files={["invoice.pdf"]}
  fields={{ profile: "Factur-X" }}
  response={{
    "invoice.pdf": { profile: "Factur-X", compliant: true, violations: [] },
  }}
/>

Each violation names the rule a PDF breaks, and where:

```json
{
  "specification": "ISO_19005_2",
  "clause": "6.1.7.1",
  "testNumber": 2,
  "description": "The stream keyword shall be followed either by a CARRIAGE RETURN (0Dh) and LINE FEED (0Ah) character sequence or by a single LINE FEED (0Ah) character. The endstream keyword shall be preceded by an EOL marker",
  "context": "object 6: endstream keyword not immediately preceded by an EOL marker",
  "severity": "fatal"
}
```

A `fatal` violation makes the PDF non-compliant. A `warning` or an `info` doesn't, such as the warnings Factur-X raises for the softer rules of its Schematron.
